# FAPROTAX2 repository architecture assessment

**Scope:** Read-only audit of the current pipeline structure for the FAPROTAX2 migration. This report maps the integration surface and validation constraints; it does not establish either mapper mode's upstream input contract or report a runtime proof of concept. Those require inspection and execution of the official mapper.

## Current pipeline boundary

The runner has one maintained module registry and one matching output-directory mapping. It sources the eight module files, loads merged YAML configuration, rejects module names outside the registry, calculates module-specific R package requirements, inventories inputs, runs module preflight, stages each requested module in isolation, checks the module result envelope and exact staged-file census, then publishes outputs into a transaction stage. The final manifest records every module, including modules not requested, and lists each owned output with its producer. See `analysis/00_run_pipeline.R:30-78`, `:298-319`, `:322-435`, and `:491-590`.

`faprotax` is already opt-in: it is absent from `parse_requested_modules()`'s default module list (`analysis/utils/config.R:32-53`). Its module is loaded from `analysis/08_faprotax.R`; dependencies and preflight are conditional on explicitly requesting it (`analysis/utils/dependencies.R:24-47`, `analysis/utils/preflight.R:548-563`). Preserve those code paths and their existing tests while adding a separately named `faprotax2` module. The module name must also remain outside the default set.

The current output directory is `08_FAPROTAX`; configuration derives it in `analysis/utils/config.R:567-578`, and the runner rebuilds the same mapping when it rebases into transaction staging in `analysis/00_run_pipeline.R:298-309`. A new output directory therefore needs to be added in both places, with one canonical `09_FAPROTAX2` mapping. The generic module staging code uses the module name and declared outputs, so the adapter should write only beneath its mapped output directory and return every created file.

## Configuration and inputs

`merge_config()` recursively rejects unknown YAML keys rather than silently accepting them (`analysis/utils/config.R:445-464`). Defaults are explicit in `get_default_config()` (`:310-413`); `validate_config()` checks them before CLI module selection (`:56-298`). A `faprotax2` configuration block and any sequence input fields must be added to defaults and validated there. Path-valued settings must be resolved against the config file directory in `load_config()` (`:544-561`); per-sample path maps use a separate resolution loop (`:553-559`). `config.example.yml` should document the opt-in interface. Keep `faprotax2` mode names, input fields, and numeric options provisional until the official package contract has been verified.

The existing analysis context is constructed from the pipeline's taxonomy abundance table and upstream classifier data (`analysis/utils/io.R`, with mode and sample checks around `:1015-1050`). Legacy FAPROTAX deliberately builds `Taxon_######` identifiers from parsed taxon rows in `analysis/08_faprotax.R` and uses the `microeco` 1.2.12 database. Those generated identifiers are suitable only for its internal taxon table. They cannot stand in for representative sequences or sequence-feature IDs. Sequence mode therefore needs a separately validated feature-to-count input whose IDs are checked against the FASTA according to the official mapper's rules. Do not join by row order or substitute species-level abundance rows for feature counts.

Input lifecycle changes are needed wherever paths are currently enumerated:

- `inventory_inputs()` fingerprints the configured primary inputs, optional phylogeny and classifier inputs, then checks them for changes during execution (`analysis/utils/preflight.R:59-142`, `:145-180`). Every new sequence, feature-count, taxonomy, mapper, or reference input that can affect results needs explicit fingerprint/provenance treatment based on its true role. Reference directories may need a deterministic inventory strategy rather than a single-file fingerprint.
- `validate_output_root()` protects configured inputs from overlap with the output root using a hand-maintained path list (`analysis/utils/preflight.R:392-425`). Add new user input paths so an output cannot overwrite them.
- `load_config()` resolves paths against the config location. Add every verified path field there; avoid shell command strings for the Windows mapper invocation.
- `io.R:1021-1035` currently rejects zero-classified samples for selected modules including legacy `faprotax`. Do not automatically apply that classifier-derived restriction to sequence mode; applicability depends on whether the mode actually consumes this abundance context.

The sequence input validation must establish, from official evidence and actual runs, header parsing, duplicate IDs, count-table schema, duplicate IDs, ID set equality and allowed unmatched IDs, numeric/nonnegative count rules, sample columns, sequence alphabet/length constraints, and taxonomy requirements if any. Negative fixtures should cover the mapper's real rejection boundary. This repository audit cannot supply those contracts.

## Runtime dependencies, preflight, and resource checks

`RUNTIME_PACKAGES` are included for all runs, while `MODULE_PACKAGES` are included only for requested modules (`analysis/utils/dependencies.R:5-35`). The lockfile comparison is calculated over the requested module package set in `analysis/00_run_pipeline.R:66-78`. The FAPROTAX2 dependency map should be module-specific and version-checked only for `faprotax2`; this lets users run the legacy module without acquiring new dependencies. If the official mapper is invoked through `Rscript`, `processx` is already in runtime dependencies, and argument vectors should preserve Windows spaces and Unicode.

Preflight runs before output mutation and has existing hooks for mode-specific runtime validation (`analysis/00_run_pipeline.R:59-113`; `analysis/utils/preflight.R:548-576`). The new module should validate that its executable/script, R runtime, reference dataset, and mode-required user files are available and compatible before staging begins. `--validate-only` currently follows this release/preflight path and is tested as filesystem-mutation-free (`tests/testthat/test-release-process.R:48-62`). Add equivalent FAPROTAX2 checks, including a path containing spaces and a missing or incompatible reference, without downloading or changing resources implicitly.

The generic workload budget currently models diversity, permutation, and phylogeny operations only (`analysis/utils/preflight.R:453-545`). It says nothing about mapper memory/CPU. After actual small native-Windows trials identify mode-specific cost, add conservative and explainable controls only if evidence supports a resource estimate. Do not claim thread or determinism behavior from configuration names or third-party examples.

## Results, manifests, and transaction behavior

Each module must return `completed`, `skipped` with a reason, or `failed` with an error. Declared paths must exist, stay under the module staging directory, and exactly match the files physically created (`analysis/utils/module_result.R:5-50`). The runner then maps each path back to a producer module and validates an exact physical census before publishing and hashing artifacts (`analysis/00_run_pipeline.R:428-435`, `:491-563`). FAPROTAX2 should emit a mode-specific provenance record containing the verified mapper/version/reference identity, input fingerprints, invocation options, and raw-output interpretation. Do not reuse legacy `FunctionReadCount` or its read denominator unless mapper evidence proves the same semantics.

Manifest validation has an exact maintained module registry in two branches: the earlier revision validator at `analysis/utils/manifest.R:317-322` and the current core at `:692-698`. Preserve the eight-module registry for historical revisions 1-5. Introduce schema revision 6 for newly generated nine-module manifests, selecting the exact registry by revision in the shared core, adding a revision-6 wrapper and dispatcher branch, and retaining the revision-3/4/5 checks. `tests/verify_release_run.R` repeats the exact list at `:230-232`, checks all manifest module keys and producer names at `:318-332`, and asserts legacy FAPROTAX output presence and skip behavior at `:366-387` and `:1087-1093`. Admit revision 6, retain count-basis checks for revisions >=5, and choose the registry by revision there too. Extend the verifier with an independent FAPROTAX2 artifact and provenance contract keyed by its selected mode, while leaving the existing FAPROTAX assertions intact. Add explicit saved-revision-5 compatibility tests and revision-6 missing/extra-key rejection tests.

If FAPROTAX2 inputs are fingerprinted in the manifest, update `validate_manifest_v2_revision1()` and the current revision core's accepted input fields and fingerprint checks in `analysis/utils/manifest.R`; the latter begins around `:529`. Add a new schema revision only if the manifest's public shape changes incompatibly. The existing transaction layer handles module staging and rollback, so new mapper outputs should remain inside the module's stage. External resources or scratch outputs must not be written to a user input path or bypass the staged ownership census.

## Test and CI integration map

`tests/testthat/test-faprotax.R` directly tests the locked legacy adapter, its 1.2.12 result schema, its denominator accounting, and its no-prokaryote skip (`:62-145`). Keep those expectations and the legacy job's configured command intact. Add a separate `test-faprotax2.R` suite. It should independently exercise each officially supported mode, input validation and negative cases, option-vector path safety, nonzero process handling/cleanup, raw value semantics, provenance, and mode-specific outputs. A test that substitutes a fake mapper can test process plumbing, but cannot count as an upstream end-to-end success.

The process tests already cover unknown and duplicate modules, validate-only immutability, and pipeline rollback (`tests/testthat/test-release-process.R`). Add targeted cases for opt-in registration, mode validation, required input failures, and no output mutation on validation failure. Manifest schema fixtures construct their own exact module registry (`tests/testthat/test-manifest-schema.R:131-161`); update those fixtures along with both manifest validators and the release verifier. These exact registries are intentional safeguards against silently omitted modules.

The workflow has Windows and Ubuntu jobs on R 4.5.3 / Python 3.12. The FAPROTAX workflow restores the locked environment, runs all `testthat` tests, then runs a full FAPROTAX integration and release verification (`.github/workflows/ci.yml:164-205`). Add an explicitly separate FAPROTAX2 integration path after deciding how the official mapper and reference can be acquired reproducibly and legally. The current workflow uses bash to call R on both OSes; native Windows proof in PowerShell remains required by the migration plan and should be recorded separately from CI's bash-shell proof. Do not add an archive or reference data to Git/CI until redistribution rights and size are established.

## Integration checklist

1. Confirm official mode contracts and license before defining configuration, output, or value schemas.
2. Add an opt-in `faprotax2` module source/registry entry, dependency checks, runtime preflight, config defaults/validation/path resolution, and separate output directory in both mappings.
3. Inventory, hash, overlap-check, and manifest-validate all result-affecting inputs and mapper/reference identity.
4. Implement taxonomy and sequence adapters only after each mode passes its independent native-Windows proof of concept. Preserve raw mapper output and describe values with the official empirically verified units/denominators.
5. Introduce the revision-6 exact registry while preserving revisions 1-5, and extend schema fixtures, release verifier, module process tests, and Windows/Ubuntu CI; retain all legacy 1.2.12 outputs and tests.
6. Validate failures, skip semantics, clean reruns, transaction rollback, exact artifact census, spaces and Unicode paths, and the new mode-specific output set.

**Boundary of this report:** No runtime or test was run as part of this read-only source audit. Taxonomy and sequence mode status remains dependent on official mapper inspection and execution.
