# FAPROTAX2 native-Windows sequence feasibility

**Phase:** P2 feasibility. This report records the initial unmodified trial findings. Later native Windows repair work is in progress only under ignored `output/`: the official MAFFT 7.526 package and pinned APPLES 2.0.11 runtime are isolated there, with a scratch mapper copy and APPLES Windows guard. A repaired single-ASV attempt has advanced through alignment but has not completed placement or functional annotation. No production code or original reference files were changed; detailed run artifacts remain ignored.

## Finding

The sequence interface is real, and a native Windows route appears achievable with narrow portability fixes. The initial unmodified one-feature trial loaded one ASV and three sample columns, then exited with status 1: the Windows gzip helper warned about an incomplete final line, MAFFT was not found, and the mapper reported that the ASV could not be aligned. It did not reach placement. The published path also has a reference-file write-target bug in a Windows-only decompression branch, the default placement engine explicitly does not support Windows, its alternate APPLES route has a Windows-incompatible startup call in the official 2.0.11 source, and its child-process commands need Windows-specific handling. Sequence mode remains **unverified and blocked**. The local probe confirms that the one-line decompression correction works on a synthetic file; later scratch work has addressed the initial tool-launch barriers but has not cleared the complete mode gate.

## Evidence and concrete blockers

1. **Windows decompression writes to the gzip input path.** In the official archive's `ensure_uncompressed()` function, the Windows branch calculates `uncompressed_file_path` but opens `file_path` for output (`faprotax.R`, lines 169–181). Sequence mode applies this function to `reference_alignments_sanitized_subset.fasta.gz` before calling MAFFT (around line 1592). I parsed the function AST from the archived source and called it only on a synthetic gzip file under ignored scratch. On native Windows R 4.5.3, the call returned a temporary `.fasta` path that did not exist and changed the synthetic `.gz` input's MD5. An in-memory scratch-only one-argument correction to `file(uncompressed_file_path, "w")` produced the expected uncompressed FASTA while preserving the `.gz` bytes. In the subsequent full mapper trial, pre/post SHA-256 manifests showed that only the disposable copy of `reference_alignments_sanitized_subset.fasta.gz` changed; the corresponding file in the unpacked official archive kept its original SHA-256. The trial copy changed from `3A21836125CAD9CC9BC0EE1CF1E62BDA2A5CF98C54EA43723EEAFF2F74DCBBE2` to `556BE9B6328AA348AAE66A03B25B79B36CF8B667DC7BDA7FADD0145C4B02F896`. The synthetic probe and pre/post manifests are in ignored `output/faprotax2-audit/sequence/`. **Required correction:** change that output target in an isolated patched mapper copy, and add a regression check that verifies both output content and unchanged compressed-source hash.

2. **EPA-NG cannot be the native Windows default.** FAPROTAX defaults to `--placement_program epang` (line 937), while the [official EPA-NG README](https://github.com/pierrebarbera/epa-ng#installation) says Windows is not supported. A native execution must select another supported route.

3. **APPLES 2.0.11 advertises Windows but fails before its Windows branch.** The [APPLES README](https://github.com/balabanmetin/apples) says it supports Windows and documents `pip install apples`; its CLI accepts the mapper's `--ref`, `--tree`, `--query`, `--output`, and `--threads` options and emits jplace output. However, the [official APPLES 2.0.11 entry point](https://github.com/balabanmetin/apples/blob/v2.0.11/run_apples.py) unconditionally calls `mp.set_start_method('fork')` near the start of `main`. It later contains a Windows branch that deliberately processes queries serially. Python 3.12 documents `fork` as POSIX-only and says an unavailable start method raises `ValueError` ([multiprocessing documentation](https://docs.python.org/3.12/library/multiprocessing.html)). That makes the unmodified APPLES 2.0.11 script incompatible with the available native Windows Python runtime before query processing begins. The source already has the intended serial Windows path. **Feasible narrow correction:** guard the `fork` selection so it runs only on platforms that support it; on Windows retain the existing serial branch. APPLES's current [`reestimateBackbone.py`](https://github.com/balabanmetin/apples/blob/master/apples/reestimateBackbone.py) selects an `apples/tools/FastTree.exe` resource on Windows, so the README's `FastTreeMP` shell example alone does not establish that a separate FastTreeMP install is required. Verify that the pinned PyPI 2.0.11 package contains and can launch the Windows resource during the native trial. No APPLES package was installed or executed here.

4. **The mapper constructs POSIX shell commands for MAFFT and placement.** In `faprotax.R` lines 1595–1597 and 1637–1645, command strings contain single-quoted paths and, for alignment, `>` redirection; both children are started with `system(command)`, and their returned status is ignored. The actual trial logged the intended alignment command, warned `'mafft' not found`, and then reported that the one input OTU could not be aligned. This confirms the sequence run is blocked when no MAFFT executable is present; because MAFFT was absent, the trial did not establish whether a Windows batch call with quoted paths succeeds. The [official MAFFT Windows instructions](https://mafft.cbrc.jp/alignment/software/windows_without_cygwin.html) provide a genuine native Win64 all-in-one package (v7.526) and state that its `mafft.bat` must be called through `cmd.exe /C` or `call` when invoked by another program. The official MAFFT [fragment-addition instructions](https://mafft.cbrc.jp/alignment/software/addsequences.html) confirm that `--auto --addfragments ... --keeplength` is a supported operation; it aligns ungapped query fragments to an existing FASTA alignment and keeps the reference alignment length fixed. The [R `system` documentation](https://stat.ethz.ch/R-manual/R-devel/library/base/html/system.html) says Windows `system()` does not provide a dependable shell-redirection interface and recommends `system2()` or `shell()` for these cases. R's [`system2()` documentation](https://stat.ethz.ch/R-manual/R-devel/library/base/html/system2.html) describes argument quoting, stdout/stderr redirection, and exit-status reporting. **Required correction:** invoke native programs using an argument vector and Windows-aware quoting; call MAFFT's batch file through `cmd.exe /C` (or a tested direct executable), capture output without ad hoc `>` shell syntax, record stderr, and stop immediately on nonzero exit before reading alignments or jplace files. Add tests with spaces and Unicode in every input/output path.

5. **The current executable checks are not a reliable Windows preflight.** The archived `check_program_exists()` calls `system(program_name)` on Windows, while `check_program_has_argument()` splits an executable-plus-arguments string on spaces and calls `system2()`. These checks do not safely model the batch-file `cmd.exe /C` invocation MAFFT requires, and splitting on spaces breaks executable paths containing spaces. **Required correction:** resolve/check the actual executable and invocation form separately; represent executable and arguments as separate values in the adapter, rather than as a shell command string.

6. **The mapper may install R packages into whichever library its process sees.** It attempts CRAN installation for `optparse`, `castor` (minimum 1.8.5), and `stringr` when they are absent or outdated. The source uses HTTP CRAN URLs. **Required correction:** preflight versions and run the mapper with an explicit isolated Windows R library so its auto-installer cannot change the legacy `renv` library. The scratch native trial set `R_LIBS_USER` to the ignored runtime library.

## Prepared local trial inputs

For the lead agent's controlled trial, I created a disposable copy of the complete official `FAPROTAX_ref_data` directory under ignored `output/faprotax2-audit/sequence/trial-ref/FAPROTAX_ref_data`. Its six files were SHA-256 checked against the unpacked archive and matched byte-for-byte before the trial. Post-run manifests confirm that only the disposable subset alignment file changed; all checked files in the original unpacked archive remained unchanged. The pre/post hashes are in ignored `ref-hashes-before.private.json` and `ref-hashes-after.private.json`.

I also created an ignored one-feature FASTA and matching OTU abundance table from one existing local sample-derived 16S ASV. Its feature ID matches exactly and the three sample values were copied from that ASV's original table column. The scratch table uses the official mapper's documented orientation (OTUs as rows and samples as columns); the source table itself was not changed. The fixture is at `output/faprotax2-audit/sequence/fixture/`. It contains private biological sequence, IDs, and sample labels; keep the directory ignored and local.

## Decision

There is no verified complete native Windows FASTA-to-alignment-to-placement run yet. The initial unmodified mapper trial exited 1 before alignment output or a jplace file; the later scratch run has passed alignment but did not complete placement or function annotation. All ongoing repair artifacts remain under ignored output. Phase P2 remains blocked for sequence mode until alignment, placement, and mapper annotation succeed end-to-end on Windows and the reference hashes remain unchanged. A taxonomy-mode success, a precomputed alignment, or a precomputed jplace file would not clear this gate.
