# FAPROTAX-mapper 2.0 upstream contract audit

**Audited:** 2026-10-24
**Scope:** Phase 1 read-only contract and feasibility audit; no FAPROTAX2 predictions were run.

## Findings

The official FAPROTAX v2 site identifies **FAPROTAX-mapper 2.0** as a beta release. Its download page distinguishes the mapper plus required reference data from **FAPROTAX-db 2.0**, which explicitly does not include the mapper or data formatted for it. The site describes the mapper as supporting both taxonomy-based and 16S-sequence-based prediction. The mapper reference set is a strict subset of FAPROTAX-db, selected for high-quality full-length 16S sequences used to build its reference tree. See the [official FAPROTAX v2 overview](https://pages.uoregon.edu/slouca/LoucaLab/archive/FAPROTAX2/lib/php/index.php) and [download page](https://pages.uoregon.edu/slouca/LoucaLab/archive/FAPROTAX2/lib/php/index.php?section=Download).

The actual official mapper archive was downloaded from [FAPROTAX-mapper_v2.0.tar.gz](https://pages.uoregon.edu/slouca/LoucaLab/archive/FAPROTAX2/SECTION_Download/MODULE_Downloads/CLASS_Latest%20release/UNIT_A_FAPROTAX_v2.0_mapper/FAPROTAX-mapper_v2.0.tar.gz) into ignored local scratch at `output/faprotax2-audit/upstream/`. It is 12,788,883 bytes with SHA-256 `859b99133b55f1e4f637e6ac14a804f3321ed27f76ee03d95e3f215382206bac`. The tar contains 22 entries and 22,612,253 bytes of uncompressed files (including AppleDouble metadata). Its top directory is `FAPROTAX-mapper_v2.0/`; there is no separate README, manifest or LICENSE file. The mapper script identifies itself as FAPROTAX v2.0. The SHA matches the independently published checksum in the third-party [microbetag Dockerfile](https://github.com/msysbio/microbetag/blob/develop/pipeline/containers/Dockerfile.faprotax2); the archive itself was retrieved from the official University of Oregon URL above.

The archive includes `faprotax.R` and the complete `FAPROTAX_ref_data/` tree: `default_config.tsv`, `reference2species_and_traits.tsv`, `tree.tre`, `tree_model.txt`, and full plus subset reference alignments. The separate FAPROTAX-db ZIP is not a substitute for this runtime reference directory. The full compressed alignment is 11,925,772 bytes and contains 26,632 sequences of 8,134 aligned nucleotides (216,624,688 bases total, about 207 MiB of raw sequence characters); the compressed subset is 57,648 bytes and contains 100 sequences at the same aligned length. The remaining reference files are approximately 4.6 MiB for the species/traits table, 4.7 MiB for the tree model, and 0.6 MiB for the tree. These are input-size observations, not a peak-RAM or runtime measurement.

## Mapper input and mode contract

The upstream CLI does **not** define `taxonomy` and `sequence` as values of its `--mode` option. `--mode` is for `normal`, `cv` or `optimize`. In normal prediction, the mapper selects its placement route based on the inputs: taxonomy placement uses `--in_taxonomies`; sequence placement uses `--in_rep_seqs` (or optional already-aligned sequences/placements). A project-level `faprotax2.mode: taxonomy|sequence` can be a useful wrapper setting, but it must select inputs and must not be passed through as upstream `--mode`.

The common input is `-i/--in_otu_table`: rows are OTUs/features and columns are samples. Classical TSV/CSV and BIOM JSON are supported; the file format follows the extension, and `.gz` is supported. For classical tables, `-k/--otu_names_are_in_column` selects the feature ID column and defaults to `OTU`; remaining abundance columns must be numeric unless the explicit omit option is chosen. The mapper can optionally emit a function-by-sample abundance table with `-o/--out_function_table`, per-feature function states with `-e/--out_otu_function_table`, annotation probabilities with `-q/--out_annotation_probabilities`, a report with `-r/--out_report`, and troubleshooting intermediates with `-j/--out_intermediates`.

Taxonomy mode is explicitly documented as requiring no sequence file. Supply taxonomy using `-t/--in_taxonomies` as `column:<column-name>` for a classical table, `metadata:<field>` for BIOM, or `file:<path>` for a separate CSV/TSV whose first column is the OTU ID and second column is taxonomy (no header required). `--taxon_delimiter` defaults to `;`. The taxonomy path is resolved on the reference phylogeny; it is not the legacy FAPROTAX 1 exact-name lookup.

Sequence mode supplies `-s/--in_rep_seqs` with a FASTA of representative **16S rRNA** sequences. FASTA sequence names must match OTU names in the abundance table; `--fasta_header_sep` defaults to a space, so the name is the header text before the first space. If the mapper sees no ID overlap, it errors. Partial missing IDs only produce a warning under verbose mode, and extra FASTA records are ignored after placement. The source does not explicitly reject duplicate FASTA IDs or require exact set equality; the pipeline adapter must validate unique IDs and its intended one-to-one feature/sequence correspondence before invocation. If no taxonomies or existing placements are supplied, the script aligns representative sequences to reference alignments with MAFFT, then places them on the FAPROTAX reference tree with EPA-NG (`--placement_program epang`, default) or APPLES-2 (`apples`). Existing user-provided alignments (`-a`) or jplace placements (`-p`) are alternate inputs; using precomputed placements alone would not test the complete representative-sequence alignment/placement path.

The package's `--Nthreads` option defaults to 0, which the script converts to detected core count. On this laptop that means up to 8 threads; the proof of concept should pass `--Nthreads 1` and explicitly inspect resource use. It should retain both the OTU-function state table and the mapper's function table so their relationship can be audited.

## Numerical behavior from source (not yet output-tested)

The default configuration contains 101 functions. Its per-function hidden-state-prediction algorithms are: Markov (43 functions), binomial (24), nearest-neighbor (22), empirical probabilities (10), and maximum parsimony (2). It sets unknown reference states to absent for 63 functions and omits unknown states for 38. The probabilistic algorithms estimate presence likelihoods; default thresholds assign presence at `>= 0.50000001`, absence at `<= 0.49999999`, and leave the tiny interval between thresholds unknown (`NA`). The nonprobabilistic algorithms assign 0/1 states. These are values read from the archived `default_config.tsv` and source, not observations from a mapper run.

By default, `--normalize none` and `--weigh_by_probability` is off. The function table is a matrix product of the OTU-function state table and the input abundance table: OTUs assigned present contribute their abundance; unknown states are treated as zero for that function. Functions can overlap, so totals across functions are not a partition of reads and must not be forced to 100%. Optional normalization changes the input OTU or output function table; optional `--weigh_by_probability` scales contributions by estimated annotation probabilities and therefore can produce fractional abundance values. Do not equate the probability output (unitless, per OTU/function) with read counts. When inputs are raw integer counts with default normalization and no probability weighting, a function's estimated abundance is the sum of counts for features assigned to that function, but overlapping functions can count the same feature more than once.

## Runtime and native-Windows feasibility

The source states it was tested with castor 1.8.5, R 4.4.2, macOS 14.5, MAFFT 7.490, EPA-NG 0.3.8 and APPLES 2.0.11. It loads `optparse`, `castor` (minimum 1.8.5), base `parallel`, and `stringr`; when missing, it attempts package installation itself. That installer targets HTTP CRAN URLs, so production invocation must use a controlled library and preflight dependencies rather than allowing an incidental write into the legacy `renv` library. The lead's Windows R 4.5.3/Python 3.12.10 baseline has `optparse`, `stringr`, and `parallel`; `castor` is not currently installed, though a compatible Windows binary is available. An explicit Rscript `--help` probe succeeded. No mapper run has occurred.

Taxonomy mode does not need MAFFT or a tree-placement executable and is **supported by the official input contract**. Native Windows execution is **still pending a positive mapper POC**, including an isolated compatible `castor` library and a real taxonomy fixture. The existing legacy library must not be mutated by the mapper's auto-installer.

Sequence mode is **supported by the official input contract**, but native-Windows end-to-end support is **unclear and currently blocked on an explicit portability trial**. MAFFT, EPA-NG and APPLES were not found on the current `PATH`. More significantly, the official script builds alignment/placement command strings with POSIX-style single-quoted paths, shell `>` redirection and `system(command)`, then does not test the returned process status before loading outputs. It was tested on macOS, not Windows. The [official R `system` documentation](https://stat.ethz.ch/R-manual/R-devel/library/base/html/system.html) says Windows `system` does not use a shell and warns that redirection/piping may not work; it recommends `system2` or `shell` for such cases. These are concrete risks for paths with spaces and for the output-redirection step. The native path must be proven with actual mapper binaries on a Unicode- and space-containing path before sequence mode can be called implemented. Do not count a taxonomy-mode run or an externally precomputed jplace file as sequence-mode validation.

The full reference alignment is about 207 MiB of sequence characters before R object overhead. The lead measured 8 logical CPUs, 8.28 GB total memory, and roughly 1.23 GB free at audit time. No memory peak or sequence-placement cost has been measured. Begin P2 with a small authorized fixture, one thread and live process/resource monitoring; avoid a large user dataset until that trial establishes a safe bound.

## Phase 1 conclusion

| Mode | Official interface | Native Windows conclusion at P1 |
|---|---|---|
| Taxonomy | Supported: abundance table plus taxonomy column/file/BIOM metadata; no representative sequences | Supported in source contract; native mapper POC pending `castor` setup and positive run |
| Sequence | Supported: abundance table plus matching representative-16S FASTA; mapper aligns and places sequences | Supported in source contract; native Windows status unclear pending actual alignment/placement trial because required tools are absent on `PATH` and process-launch code is not Windows-verified |

This report records contract evidence only. The next gate must independently execute taxonomy and sequence POCs, capture raw outputs and process status, verify identifier failures, and test repeatability/offline behavior before production integration of either mode.
